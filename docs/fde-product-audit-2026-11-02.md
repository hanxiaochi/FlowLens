# FlowLens 1.1：需求研究与 FDE 产品审查

审查日期：2026-11-02。代码基线：`598811a`，公开演示基线：`5f50dfc`。本文件是审查与候选路线，不是已完成功能清单。

## 结论

FlowLens 已有一个有价值的入口：让业务人员带着已有表格理解和试运行业务。它目前更接近“业务建模与沟通工作台”，距离可以支撑 FDE 交付的工具还有明显断点。

最重要的下一步是让**同一份业务定义**贯穿原表、字段、流程、数据变化、接口、验收和交付。当前表单与交互实验室各自运行，正好断在这条链中间。先补这条链，比继续增加展示效果或宣称一键开发更重要。

FDE 的工作包括理解客户问题、处理真实数据、构建并部署解决方案以及对结果负责。[S1] FlowLens 可以降低业务发现和设计验证的门槛，但不能把会操作 demo 等同于具备生产交付能力。

## 研究方法与证据边界

本轮进行了 11 组检索，主题包括 FDE 职责、内部工具、审批权限、退回重提、审计、文档导入、打印、数据源、失败重试、移动表单和环境交付。以下保留 12 个直接核对的官方资料、用户原帖或问题记录。

这不是全网遍历或统计意义上的热门需求排名。搜索会偏向公开社区，论坛评论包含厂商自荐，不能把评论数量当作采购意愿；厂商功能文档只能证明实现基准，不能单独证明需求热度。日期较早的帖子仅用来识别持续存在的工作模式；已关闭问题不描述为竞品当前故障。没有访问用户私有业务资料，也没有用真实监理原件作为搜索内容。

## 外部需求与我们的差距

| 可核对的信号 | FlowLens 当前状态 | 产品推论 |
| --- | --- | --- |
| 用户希望替代邮件审批，要求清楚的角色、状态与可调整数据模型。[S2] | 有本地角色推演和状态，表单无结构化字段类型 | 先把角色、字段和规则组成一份可审核定义 |
| 审批权限与所属公司、当前登录人有关；一个相关 NocoBase 问题已关闭。[S3] | 角色下拉框不是登录，也没有记录范围权限 | 做真实试点前必须验证“谁能看哪份数据”，不能只验证按钮权限 |
| 用户要让客户看审计记录，但不能因此授予管理员权限。[S4] | 本地历史可追溯，但可编辑工作包，不是可信审计 | 审计查看权限与办理权限分离，服务端记录操作者与版本 |
| 两级审批退回后，重提无法再次触发的用户报告。[S5] | 已支持退回填报人和重提，覆盖基本测试 | 这项应保留为核心验收；继续加入撤回、作废、会签、代理等经确认的例外 |
| 用户需要把单据与审批信息一起打印。[S6] | 独立 HTML 已包含历史；纸张/PDF 分页尚未验收 | 打印、签署与归档是业务出口，不能停留在页面截图 |
| Budibase 的数据源可以在应用和自动化中复用。[S7] | 表单数据与原型数据分离，不能连接现有业务数据 | 统一模型后，优先连接一个 CSV/REST 测试数据源，不先堆连接器数量 |
| n8n 官方讨论超时重试造成重复副作用。[S8] | 原型有重复执行保护，但表单尚无真实服务端集成 | 未来连接器必须设计业务操作 ID、去重、结果查询和恢复 |
| NocoBase 审批节点允许按办理阶段编辑字段并保存对应快照。[S9] | 已有阶段字段和快照，流程仅顺序节点 | 差异点应是从原表快速确认业务，而非再造完整审批平台 |
| Appsmith 将版本、回滚、环境与协作纳入交付流程。[S10] | 项目包可导出，不能部署为真正的表单业务服务 | 交付包要包含版本、迁移、验收和运维责任 |
| Confluence 的 Word 导入格式问题仍有公开记录。[S11] | 保留结构，但不完整保留图片、文本框和样式 | 导入需有原件对照、差异清单和人工确认，不承诺无损转换 |
| Appsmith 曾直接回应跨环境迁移时必须重建应用的用户诉求。[S12] | 能备份，但业务工作包与原型项目格式不同 | 让用户能带走可维护资产，而非只能带走截图与演示 |

## 代码与产品审查

“确认”表示从当前实现或可执行探针得到证据；“风险”表示源码显示危险路径，但本轮未通过故障注入或真人测试复现。

| 编号 / 优先级 | 发现与证据 | 影响与验收要求 |
| --- | --- | --- |
| F01 / P0 / 确认 | `forms-ui.js` 独立维护 workspace；`studio.js` 的 `brief()`、`openApi(model)`、`sqlSchema(model)`仍使用原型 model。探针在虚构工程表存在时导出的仍是 employees/leaves 接口 | 用户可能把别的示例架构当作自己的表。必须让原表字段能追到实体、接口与事件；未关联时明确显示当前上下文并阻止误导性交付 |
| F02 / P0 / 确认 | `forms-ui.js` 的 `addInput()`统一创建 textarea；`forms-model.mjs`校验的是字符串长度和必填 | 检查日期、金额、数量都没有类型语义。必须支持类型、单位、枚举、引用、重复明细和服务端等价校验；不自动判定工程质量 |
| F03 / P0 / 风险 | `forms-store.mjs`直接 put 整个 current 工作包，没有预期版本检查；单标签 saveTail 不跨标签共享 | A、B 同时打开后，后保存者可能覆盖前者。增加原子版本比较，冲突保留草稿并提示重载/合并；测试两个独立连接的交错写入 |
| F04 / P0 / 风险 | `forms-ui.js` 的 `act()`和附件等路径先替换内存数据，后 await persist；失败没有统一事务回退。只在外层捕获错误 | 磁盘失败时，内存、页面和存档可能不一致。采用提交成功后替换状态；失败时仍可保留和导出未提交草稿；注入配额失败、事务 abort 验证 |
| F05 / P0（上线前）/ 确认 | `forms-model.mjs`按传入 role 检查权限；数据在 IndexedDB，没有表单后端 | 本地模拟边界合理，但不具备多人生产权限。上线试点必须有服务端身份、项目范围隔离、负向权限测试与日志 |
| F06 / P1 / 确认 | 同一实例有快照；新模板字段/流程仍靠逐格配置，规则没有出处和业务确认记录 | 340 表能导入，不等于340表能快速实施。增加字段建议、批量确认、未识别项、来源定位；统计人工修正时间而非只统计表数量 |
| F07 / P1 / 确认 | `forms-model.mjs`顺序 step++，return 到 draft；relatedId 是单条引用 | 关联指令和回复不等于业务闭环。优先明确拒绝终止、撤回、退回目的地、条件分支；会签/代理/超时按试点需求逐步加入 |
| F08 / P1 / 确认 | 业务台账只有搜索；没有待我办、期限、提醒或跨表汇总 | 能演示流转但难以每天办事。先增加待办、当前负责人、截止时间和积压视图，并明确真实通知是否发送 |
| F09 / P1 / 确认 | 开发交付主要是原型 Markdown、OpenAPI 和 SQL；表单包不含可运行后端 | 开发者仍要重新解释业务。交付必须带映射、未确认问题、权限矩阵、测试样例与部署/迁移说明 |
| F10 / P1 / 未验收 | 窄屏 CSS 已存在，但上轮浏览器尺寸覆盖未生效；表格有550px最小宽度，多处字号9–12px | 现场手机填写、键盘操作、放大阅读未获实测证据。手机用适配表单视图，原表用于核对与打印；增加真机、键盘与200%缩放验收 |
| F11 / P1 / 确认 | 有假设列表和备注，但没有业务目标、当前耗时、验收责任人和结果对比的结构化流程 | 容易只交付漂亮演示。增加业务访谈卡、验收案例和基线指标，展示方案是否改善原流程 |
| F12 / P2 / 确认 | 当前无明确项目许可证；英文 README 与视频不等于英文 UI；生产运维与接手责任未建立 | 外部采用与贡献有阻力。许可证需要作者选择，不能擅自替作者授权；国际推广前补齐使用界面与文档一致性 |

P0 指下一阶段基础工作或正式上线的阻断项，不代表公开本地 demo 必须立即具备完整企业后台。本轮没有进行渗透测试、负载测试或外部真人可用性测试。已有54项测试是已有逻辑的证据，不覆盖以上所有风险。

## 已执行的核对

用当前模块运行只读探针：`demoWorkspace()`生成“现场检查与资料流转单”，含施工单位、合同段、检查日期、监理意见等字段；`example()`的实体仍为“员工、请假申请”；`openApi(example())`导出`/api/employees`与`/api/leaves`路径。这确认 F01，不是对用户操作的猜测。

F03/F04 本轮只做源码审查，未声称实际发生数据丢失。修复需要存储故障与并发回归测试，不能简单加提示就视为完成。

## 产品定位与取舍

建议定位：**帮助业务人员和实施工程师，把已有业务材料变成可验证、可交付的系统定义。**

业务人员负责解释规则、确认字段、判断实际价值；工具负责保存证据、显示变化、运行案例；工程师负责集成、权限、可靠性和上线。这使非技术人员能参与真实交付，而不是让他们误以为不需要工程责任。

“表格 + 工作流”是管理系统很好的入口，但完整业务还涉及主数据、权限、计算规则、检索统计、外部系统、归档和运维。不要把纸面每个格子一对一变成数据库字段：同一个项目名称可能出现在很多表，明细行可能是子表，签字可能是一条签署事件。

保留原表视图和3D讲解，但让它们都来自同一份业务定义。暂缓更炫的3D场景、几十种连接器、自动生成所有后端框架、把简单审批升级成自主执行代理。一个能可靠打通的业务链比大量浅层入口更值得验证。

## 建议路线（尚未实现，不是工期承诺）

### 第一关：1.2 候选——一份业务贯穿全过程

1. 统一业务定义：稳定的字段/实体/动作ID、原文定位、字段类型、规则来源、确认状态、schema版本。
2. 表单、流程图、数据图、按钮执行和开发说明都引用该定义；保持旧版工作包可导入，迁移前预览、备份。
3. 修复F03/F04，再增加保存状态、冲突处理与恢复入口。
4. 生成基于当前业务的验收案例：成功、缺字段、错误角色、退回重提、重复提交、失败恢复。

通过标准：导入一张新的脱敏复杂表，字段改名后表单、图、接口和测试引用仍一致；点击提交显示该业务的真实模拟事件，不跳回员工请假；未确认规则不能伪装成已验证能力。

### 第二关：1.3 候选——连接一个真实测试环境

只选择一个可控目标：受限 REST 接口或一套数据库测试环境。先只读预览、字段映射，再开放测试数据写入。密钥留服务端；每次操作有业务ID与关联日志；超时查询结果而非盲重试；重试不能产生重复业务。

同时补CSV/Excel数据迁入、数据冲突报告、待办和最必要的异常分支。不要把“新增连接器”当成业务已经接通。

通过标准：另一位实施者使用交付包完成安装/连接，在不修改内核源码的情况下运行指定场景；服务重启后数据仍在；两名用户权限隔离；重复请求只产生一次效果；恢复演练有证据。

### 第三关：行业试点——有人每天愿意使用

选择三个高频模板，完成真实多人权限、文件存储、备份、移动使用、正式归档与部署责任。只有业务方确有需要时接入电子签章。先试点，再讨论平台化与商业化。

## 用监理场景做一次完整验收

选“指令 → 整改回复 → 复查 → 归档”，由业务人员确认实际适用规则。不要把一般通知自动当成必须回复的指令。

1. 指令关联统一项目与合同；回复引用原指令，避免重复手填基础资料。
2. 附件和回复属于具体业务版本；监理能看到其审核的是哪份数据。
3. 资料不足退回并说明原因；修改后重提保留同一业务编号和前后差异。
4. 复查不通过走确认后的补充整改路线；通过后归档，保留原件与历史。
5. 未授权人员看不到另一个项目；重复提交不重复建单；失联时不给出虚假的完成状态。
6. 另一个实施者从交付包接手，能改一个已确认规则、运行测试、发布并回滚。

## 如何判断真的让用户前进一步

以下是待验证门槛，不能宣传为已达到：

| 参与者 | 任务 | 建议观察指标 |
| --- | --- | --- |
| 5位非技术业务人员 | 用脱敏原表确认字段、办理人和一个退回场景 | 至少4人能完成；记录首次完成时间和求助次数，不预先宣称“一分钟完成” |
| 2位实施/开发人员 | 仅凭交付包解释并运行同一业务 | 不重新录入字段；指出所有未确认规则；无源码口头补充仍能接手 |
| 试点负责人 | 对比原处理方式与新流程 | 实际办理耗时、退回次数、重复录入、遗漏待办；使用前先测基线 |
| 维护人员 | 修改规则并恢复旧版 | 旧记录不损坏，测试结果和迁移影响可追踪 |

“看得懂 → 说得清 → 验得出 → 交得走 → 改得动”可以作为阶段目标。第一步不要求人人成为全栈工程师，但每一步必须有能检查的产物。
